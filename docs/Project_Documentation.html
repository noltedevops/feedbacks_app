1. What Is This Project? (Plain-Language Overview)

This project is a field data-collection and visualization platform built for Nolte Geoservices GmbH, a German geophysics company. Its purpose is to support UXO clearance work — the process of finding and safely removing unexploded ordnance (old wartime bombs, mines, and munitions) buried in the ground before construction work begins.

The concrete use case is a real project: “11-24-2736 — Wilhelmshaven Rüstersieler Seedeich”, a sea-dike site in Wilhelmshaven, northern Germany. The workflow it supports looks like this:

  1. Survey phase (already done, outside this app). Geophysicists scan the site with two instruments — georadar (ground-penetrating radar, GPR) and magnetometers. Each suspicious underground signal is recorded as an anomaly (also called a target): a point with coordinates and an estimated depth. These results arrive as CSV exports (Radar_data.csv, Magnetic_data.csv).
  2. Loading targets into the platform. A Python script (ingest_anomalies.py) cleans, merges, and loads the anomalies from both instruments into a central PostgreSQL/PostGIS database. The raw CSVs contain ~2,430 magnetic rows and ~45 radar rows; after dropping rows with missing or duplicate coordinates, the live database currently holds 1,583 anomalies and 61 feedback records.
  3. Field investigation. A field worker opens the web app on site, sees all targets on an interactive map, walks/digs to each one, and records what was actually found: the excavated depth, dimensions of the hole, the object found (iron bar, wire, nothing, etc.), photos, notes, and the crew and equipment used. This works even without an internet connection — entries are stored in the browser and synced later.
  4. Office monitoring. Back at the office, an analyst sees live progress: how many targets are investigated, what was found, charts comparing predicted vs. actual depths, excavated volume, and a map coloured by status. The same surface exports the official Öffnungsmaßnahmen report as PDF or CSV.

In one sentence: it is an offline-capable “ArcGIS Field Maps”-style web app plus backend, purpose-built for tracking the investigation of suspected UXO targets and syncing field findings with a central geospatial database.

1.1 Who may see what

Access is granted per surface, not per job title. Every account carries three independent flags — can_field, can_dashboard and is_admin — and the server re-checks them on every request. A user who opens a surface they lack is offered a permission request, which an administrator approves or denies in the app. The older role value survives only as the landing view and the label shown in the sidebar; it no longer decides anything.

Why this shape?

  • The field has poor connectivity, so the browser keeps its own full copy of all targets in IndexedDB and queues unsent work. The server is the single source of truth once syncing succeeds.
  • The office uses professional GIS tools (QGIS, ArcGIS Pro) that talk to PostGIS directly. Database triggers make sure a point moved in QGIS updates lat/lon for the web app, and a point dragged on the web map updates the PostGIS geometry — bidirectionally.
  • One deployable unit: the built React app is written into ./static and served by FastAPI itself, so a single python server.py serves both the API and the UI on port 8000. Because both come from one origin, the frontend calls /api/... with an empty base URL and there is no host to configure.
  • The asymmetry is deliberate: the field app is built to survive with no network; the dashboard is not. Analytics and reports are read straight from the server, because a stale dashboard is worse than an unavailable one. The crew's own work is never blocked that way.

Stable IDs — a deliberate design choice. Anomaly IDs are not random. They are uuid5(NAMESPACE_DNS, target_id), i.e. a hash of the project + coordinates. Re-running the ingestion or the seed always produces the same IDs, so feedback recorded against a target never becomes orphaned when the target list is reloaded. (Commit b39c85b introduced this.) models.py also declares a uuid4 default on the column, but no insert path reaches it — every one passes an explicit uuid5. Verified in sql/append_anomalie_1_to_anomalies.sql: recomputing the rule for all 1,583 stored rows reproduced every id with zero mismatches.

6.6 Additive migrations

create_all creates missing tables but never alters existing ones, so columns added after a database was first seeded have to be added explicitly. init_db() does this by hand for feedback.teams_tools and for the four user flags, checking information_schema (or PRAGMA table_info on SQLite) first. The backfill runs only for columns that particular run added — dashboard-only accounts lose can_field and gain can_dashboard once — so a later edit to somebody's access is never overwritten on the next startup.

6.7 The spatial synchronization trigger

database.py → init_db() installs a PL/pgSQL trigger (sync_anomaly_geom_and_coordinates) that fires before every insert/update on anomalies and keeps all three coordinate representations consistent, whichever one was edited:

  • Case 1 — geom changed (e.g. a point moved in QGIS/ArcGIS Pro): recompute easting/northing and, via ST_Transform(..., 4326), latitude/longitude.
  • Case 2 — easting/northing changed (e.g. edited numerically): rebuild geom and lat/lon.
  • Case 3 — latitude/longitude changed (e.g. a marker dragged on the web map): rebuild geom in UTM 32N and easting/northing.

Case 2 is why an insert that supplies its own lat/lon but leaves geom null will have those values recomputed from SRID 32632 — intentional, so every row obtains its coordinates the same way. See sql/append_anomalie_1_to_anomalies.sql, which measured the resulting divergence at at most 0.0069 m.

7. The Backend Server (FastAPI)

server.py is the whole backend — about 1,210 lines. On startup it:

  1. Calls init_db(): connects to the database, enables PostGIS, creates missing tables, applies the additive column migrations, and installs the sync trigger.
  2. Creates the FastAPI app titled “Nolte Geoservices UXO Target Sync Platform”.
  3. Runs a lifespan hook — replacing the deprecated @app.on_event handlers — which seeds the default accounts, but only into an empty users table.
  4. Enables fully-open CORS (any origin/method/header) — convenient for development, still to be tightened for production (§17).
  5. Mounts ./static at /, so the compiled React app is served by the same process.

7.1 Connecting to the database: fail loudly

This behaviour was inverted on 19 August 2026 and is the single most important operational change in this revision.

  • The first connection is retried for DB_CONNECT_RETRY_SECONDS (default 30). A cold boot starts this process and the database together, and Postgres needs a few seconds before it accepts connections; nothing supervises this process, so a single attempt would turn an ordinary race into an outage lasting until somebody restarted the app by hand. Set it to 0 to fail on the first attempt.
  • A failed connection is now fatal. The app previously fell through to SQLite unconditionally, which turned a wrong password or an unreachable server into an app that started cleanly against an empty database: the data was simply absent, every login failed, and the real cause sat in one warning line among the startup output.
  • The SQLite fallback is opt-in, for deliberate offline work only, via ALLOW_SQLITE_FALLBACK=1. See the gotcha in §15 — it is read from the process environment, not from .env.
  • The connection URL is masked in every log line (safe_url()). These lines run on every startup into terminal scrollback, log files and CI output; rotating a password and keeping it out of git achieves nothing if the app prints it each time it starts.

config.py additionally compares POSTGRES_PASSWORD against the password inside DATABASE_URL and prints a warning when they disagree — percent-decoding the URL's copy first, so an escaped password does not read as a mismatch. It warns rather than fails, because a volume whose password was rotated with ALTER USER sits in that state legitimately.

7.2 Authentication and authorization

Passwords are hashed with PBKDF2-HMAC-SHA256 from the standard library — no external crypto dependency to install on a field laptop — and stored as pbkdf2_sha256$<iterations>$<salt>$<hash>. Stored hashes are transparently re-hashed on login when the iteration count moves. Session tokens are HMAC-signed with AUTH_SECRET; if that is unset a random key is generated per process, so every restart signs everyone out.

Authorization is enforced by four FastAPI dependencies:

DependencyEffect
current_userA valid bearer token is required.
require_surface("field"|"dashboard")The matching access flag is required. The 403 body carries the surface name, so the client can offer to request that permission rather than showing a bare error.
require_any_surface(...)At least one of several surfaces. Used for the CSV export, which both apps legitimately offer — requiring dashboard there locked collectors out of a button their own screen shows them.
require_adminis_admin is required.

Every one of them first blocks a user whose must_change_password flag is set. Request and response shapes remain Pydantic models: UserRegister, UserLogin, FeedbackCreate, PointCreate, PointUpdate, SyncPayload, TeamsTools, UserAccessUpdate and PermissionRequestCreate.

7.3 Default accounts

Seeded only into an empty users table, and given the password in SEED_PASSWORD. If that is unset, each account receives its own random password, which has to be reset rather than guessed. Once any account exists, SEED_PASSWORD has no effect at all.

8.3 Targets and synchronization

Method & PathGuardBehaviour

For each anomaly, finds the newest feedback row (by visit_date), derives a display status (§13), parses the photos JSON, and returns one combined object per target. Incoming ISO-8601 Z timestamps are normalised to naive UTC to match the column type. Marks each anomaly investigated, applies coordinate updates, and responds with counts plus a fresh full point list so the client refreshes its cache in the same round-trip. On commit failure it rolls back and returns HTTP 400.

10. The Data Ingestion Pipeline (ingest_anomalies.py)

This script performs the initial bulk load of survey results into PostgreSQL. Steps:

  1. Read Radar_data.csv (georadar) and Magnetic_data.csv (magnetometer) with pandas, auto-detecting whether the separator is ; or ,. It prefers georadar.csv / magnetic.csv if those exist, so a newer export can be dropped in without renaming.
  2. Tag & merge: add an instrument discriminator column to each set, concatenate them, and rename the German survey columns (Rechtswert→easting, Hochwert→northing, Tiefe [m]→evaluated_depth).
  3. Clean: drop rows missing coordinates; fix a known systematic coordinate error in the “Stoerkoerper Magnetik Sued 2” layer (easting short by 397,000 m, northing off by +21,000 m); drop duplicate coordinates, since target_id is derived from the position and is UNIQUE.
  4. Enrich: assign project_id, status='pending', category='Kat-1', sequential vm_nr labels, coordinate-derived target_id strings, deterministic UUIDv5 ids, and WKT point geometry text.
  5. Load: drops and rebuilds the three data tables (destructive!), re-creates them via init_db() (which also reinstalls the trigger), seeds the project row, bulk-stages the DataFrame into a temp table with to_sql, then inserts into anomalies converting WKT to PostGIS geometry with ST_GeomFromText(..., 32632).

Warning. Both ingest_anomalies.py and POST /api/seed erase existing anomalies and feedback before loading. Never run them against a database holding real field data you want to keep. Take a dump first — see §16.

Two things that will bite you. The script resolves Magnetic_data.csv, Radar_data.csv and .env as bare relative paths against the current working directory, so it must be run from the repository root and the CSVs must stay there. It also imports pandas, which requirements.txt does not pin — install it separately.

10.1 The other ingestion paths

POST /api/points/import is the additive alternative, backing the Import tab in the UI. POST /api/seed loads demo data only. Both hardcode project 11-24-2736.

10.2 SQL migrations (sql\)

Hand-written, single-purpose SQL for bringing an additional project's data into public.anomalies — records of specific migrations that were run, not a migration framework. anomalie_1_from_picks.sql builds a staging table shaped like public.anomalies from a picks table; append_anomalie_1_to_anomalies.sql appends those 127 rows in one transaction, with ON CONFLICT DO NOTHING so a re-run is a no-op.

The second file is worth reading before writing anything similar. Two of its findings generalise: Postgres cannot compute UUIDv5 here (it needs SHA-1, which core Postgres lacks, and neither pgcrypto nor uuid-ossp is installed), so the ids are precomputed in Python and carried in a CTE rather than installing an extension on production; and the BEFORE INSERT trigger overwrites any lat/lon you supply when geom is null (§6.7).

11. The Frontend Web Application (React)

The UI is a single-page app with two surfaces, both sharing one collapsible sidebar (theme toggle, EN/DE language toggle, navigation, sync button, online/offline indicator, user avatar, sign-out). Which surfaces a user may open is decided by their access flags, not by a role picked at login.

11.1 Login / landing page

Changed since the previous revision. The 16 July 2026 edition of this document stated that “authentication is demo-grade only: any username/password is accepted… There is no server-side auth at all.” That is no longer true.

A full-screen landing page styled after ArcGIS Field Maps: company logo, project description, and a Sign-in modal with login and sign-up views. Authentication is now real:

  • Credentials are checked server-side against a PBKDF2 hash, and a signed token is returned. auth.ts attaches it as a bearer token on every API call via authFetch.
  • The access flags mirrored into localStorage decide only what the UI offers — the server re-checks them on every request, so a flag flipped in devtools buys nothing.
  • Opening a surface the account lacks raises a permission request dialog instead of an error; an administrator decides it in the app.
  • A user carrying must_change_password gets a non-dismissible password dialog — the server refuses every surface until it is done.
  • Admins additionally get a user-administration dialog (flags, temporary passwords) and the permission-request queue.

Signing in with no network

Nobody can verify a password offline, so auth.ts records every account the server has authenticated on this device. Offline, only such an account may sign in, and it is granted the field app only — the dashboard and admin screens are server-backed and could otherwise display data the person is no longer allowed to see. That record deliberately outlives sign-out: it describes what this device has learned, not who is signed in now, and signing out must not turn the device back into one that will accept an unknown name offline.

Three implementation notes worth keeping in mind before editing the layout:

  • One breakpoint, two languages. useIsMobile.ts exports MOBILE_BREAKPOINT = 768 and the CSS overrides key off the same number, so a layout can never be half-switched. The hook exists only because the dashboard's desktop layout floats absolutely-positioned panels over the map: the map is not a sibling in the flow, so no media query can reorder it into a reading column. It uses useSyncExternalStore over a single shared matchMedia object, so the first render already sees the correct breakpoint instead of painting the desktop layout and correcting it.
  • The landing page needed inline styles overridden. Its layout lived in inline style attributes, which beat any stylesheet rule at any specificity — which is why landing.css had no layout media queries at all. At 375px the showcase column was laid out fully outside the viewport and then clipped by overflow-x: hidden, so the carousel was missing rather than merely squeezed.
  • Leaflet has to be told its container changed. Leaflet measures its container once, at creation, and never notices it changing; tiles for the area outside the original box are never requested, which is what the grey panels were — the map was not broken, it did not know it had grown. invalidateSize was called nowhere in the codebase. A ResizeObserver on the container now catches the phone reflow, a drawer opening beside the map and a panel stacking below it; orientationchange is listened for separately because on a phone it can arrive before the box has settled. Calls are coalesced to one per animation frame, since a rotation fires the listeners repeatedly and invalidateSize forces a synchronous re-layout every time.

Do not remove the cssTarget pin in vite.config.ts. Left unpinned, esbuild minifies media queries into range syntax — @media (max-width: 768px) becomes @media (width<=768px) — which Chrome <104, Safari <16.4 and Firefox <102 do not parse. Those browsers discard the whole at-rule, which silently takes every mobile rule in index.css with it and leaves a phone rendering the desktop layout. The landing page survives it because it is fluid by default; the dashboard and field app do not.

11.5 Small fixes worth recording

  • Avatar initials. All three call sites built initials by slicing the first two characters off one string, so “Emmy Blaize” rendered as EM instead of EB, and the seeded “Operations Analyst” as OP. It only ever looked right for people whose first two letters happened to match their initials. A single initialsFor() helper now takes first initial + last initial for a full name and keeps the first-two-letters behaviour for a single token, which the username fallback relies on for values like admin. Whitespace runs are collapsed before splitting, and the string is walked by code point so a name starting outside the BMP is not cut in half.
  • EN/DE translation. i18n.ts is a lightweight lookup where the English string is the key: t('Field App') returns the German text in DE mode and falls back to the key itself when no translation exists.

12. Offline-First Design & Synchronization

This is the heart of the app. Two independent mechanisms are involved, and they are easy to confuse: the service worker caches the application shell so the app opens offline; Dexie caches the data so it is usable offline.

12.1 The browser database (Dexie / IndexedDB)

indexedDb.ts, database name NolteFieldDb, version 2, three tables:

TableContents
pointsThe full local mirror of all targets (+ their latest feedback), refreshed from the server whenever online.
pendingFeedbackOutbound queue: feedback entries created while offline, or not yet accepted by the server.
pendingPointUpdatesOutbound queue: coordinate corrections from dragged markers.

Reads always come from Dexie, never directly from the API, so the UI has no online path to special-case.

12.2 The synchronization lifecycle

  1. On login (online): fetchFromServer() pulls GET /api/points and rewrites the local points table.
  2. Recording feedback: handleSaveFeedback() always writes to the pending queues and optimistically updates the local point — the marker turns green immediately, network or not.
  3. Connectivity monitoring: the app listens to the browser's online/offline events and shows a toast plus an indicator in the sidebar.
  4. Auto-sync: whenever the app is online, logged in, and the pending count > 0, handleSync() fires automatically (also available as a manual sidebar button with a badge showing the queue size). Background runs are silent — the crew did not ask for them, and a failure is harmless because the records stay queued.
  5. Snapshot semantics: the run captures the ids it is sending and, on success, deletes only those. A record queued while the request was in flight survives for the next cycle, and an accepted record is never re-sent.
  6. Coalescing: saving a record starts a sync and bumps the counter the auto-sync effect watches, so two cycles used to POST the same row concurrently and the loser came back as a duplicate-key HTTP 400. A run now in flight absorbs whatever was queued behind it.
  7. Conflict handling: the server upserts per feedback id and refuses to let an older visit_date overwrite a newer one, and silently skips feedback whose target no longer exists (logging a warning).

12.3 The service worker (app shell)

frontend/public/sw.js, cache uxo-tracker-v2. Registered from main.tsx on window load.

  • Install precaches /, /index.html, /manifest.json, /favicon.svg and the Google Fonts stylesheet.
  • Activate deletes every cache whose name is not CACHE_NAME, and claims open clients. Renaming the cache is therefore how a bad one is evicted — bump it whenever the precache list changes.
  • Fetch: /api/ always goes to the network and is never cached. Everything else is stale-while-revalidate — a cached response is served immediately and refreshed in the background; a miss goes to the network and is cached if it is a basic 200, which is what captures Vite's hash-named JS and CSS. A failed navigation falls back to /index.html.

Why offline mode was broken, and what fixed it (19 August 2026). cache.addAll() is atomic: a single failed request rejects the whole call, which rejects the waitUntil promise, which fails the install event, so the worker never activates and nothing at all is cached. The precache list carried a stale /favicon.ico — inherited boilerplate; there has never been a .ico in this repository, index.html has always shipped an SVG favicon. That one 404 was silently costing the app its entire offline mode while register() still resolved and logged success in the page.

The fix removes the stale entry and switches to caching each asset individually with Promise.allSettled, logging Precache skipped: for any that fail. One unreachable URL now costs only that asset. This matters beyond the favicon: the font stylesheet is cross-origin, so a crew installing the app somewhere with no signal would otherwise end up with no offline shell at all — the exact situation this app exists for. The cache was renamed from v1 to v2 so the activate handler drops the empty cache already sitting on installed devices.

Map tiles are third-party and are not precached: only tiles already fetched while online remain available. Target markers come from IndexedDB and work regardless.

Prerequisites

  • Python 3.13 with pip (the repository uses a virtualenv at .venv)
  • Docker Desktop, for PostgreSQL/PostGIS and pgAdmin. No longer optional — the app refuses to start without a reachable database unless you deliberately opt into the SQLite fallback.

Step 1 — Configure

Copy the committed template and fill it in:

copy .env.example .env

.env.example is the source of truth for every setting. It carries the explanation next to each key, and this document deliberately does not restate values. .env is gitignored and is read by two different consumers: pydantic-settings (the application) and docker-compose (the containers). Read §15 before choosing passwords — there are three of them and they are not interchangeable.

Credentials for both come from .env; compose uses the ${VAR:?message} form, so a missing value fails the command with that message instead of quietly falling back to a well-known default. Inside pgAdmin, register a server with host db (the compose service name), port 5432, and the user and password from your DATABASE_URL.

15.1 The three passwords

Three different things that happen to look alike, and confusing them has cost real time:

PasswordConsumerEffective when
POSTGRES_PASSWORDPostgres initdb, via composeFirst creation of the postgres_data volume only. Inert thereafter.
the password inside DATABASE_URLthe applicationEvery connection. This is the one that makes logins work.
PGADMIN_DEFAULT_PASSWORDpgAdmin, via composeFirst creation of the pgadmin_data volume only.

config.py warns when the first two disagree. It warns rather than fails, because a rotated volume legitimately sits in that state — but it still matters, because a recreated volume would be initialised with POSTGRES_PASSWORD and the app would then be unable to connect with the DATABASE_URL it has.

ALLOW_SQLITE_FALLBACK is not read from .env. database.py reads it with os.getenv, and nothing in this project loads .env into os.environ — the application reads that file only through pydantic-settings. Putting the variable in .env therefore has no effect whatsoever. Set it in the shell instead:

$env:ALLOW_SQLITE_FALLBACK = "1"

The same is true of DB_CONNECT_RETRY_SECONDS. (ingest_anomalies.py is the one exception in the repository: it has its own hand-rolled loader that does populate os.environ.)

15.2 pg_hba and trust authentication

initdb writes trust for local and 127.0.0.1 connections by default, meaning any process inside the container reaches the database as superuser with no password. The compose file therefore sets POSTGRES_INITDB_ARGS: "--auth-local=scram-sha-256 --auth-host=scram-sha-256", so a freshly created volume comes up requiring a password. The existing running volume was corrected in place — that setting cannot retroactively change a volume that already exists. doctor.py re-checks this on every run.

16. Troubleshooting

Run this first. .venv\Scripts\python scripts\doctor.py — whenever the app will not start, logins fail, accounts appear to be missing, or pgAdmin refuses you. It codifies the checks that were previously done by hand, one shell command at a time, the last time nobody could log in; that session turned up three separate causes at once — a stale POSTGRES_PASSWORD, a pgAdmin password that had never been applied, and pg_hba still on trust — none of which announced themselves.

It is read-only: it connects, reads and reports, and changes nothing. It prints no password; where one must be identified it is named by origin (“DATABASE_URL”), never by value. pgAdmin is inspected by reading its database, never by attempting a login, which would count against the lockout threshold and could lock the very account being diagnosed. Exit status is 1 if any check fails, so it can gate a deploy or run in CI.

CheckCatches
POSTGRES_PASSWORD vs DATABASE_URLA rotation applied to only one of them.

Logins fail, or the accounts are gone

Almost always the database connection, not the accounts. In order of likelihood: the app is running against the SQLite fallback — an empty database with no users, which doctor.py reports explicitly; DATABASE_URL carries a password Postgres does not accept; AUTH_SECRET is unset or was changed, so existing sessions no longer verify; or the account genuinely lacks that surface. To get back in without the web app:

.venv\Scripts\python manage_access.py list
.venv\Scripts\python manage_access.py grant <username> --admin --dashboard
.venv\Scripts\python manage_access.py set-password <username>

The CLI refuses to revoke the last administrator, needs an interactive terminal for set-password (it will say so rather than hang on a pipe), strips the trailing carriage return MinTTY can hand back — hashing that would store a password nobody could ever type again — and re-reads the row afterwards to verify the new password against the stored hash.

The app refuses to start: “Cannot reach the database at …”

Working as intended (§7.1). Fix the connection; run doctor.py. Only set ALLOW_SQLITE_FALLBACK=1 for deliberate offline work, and remember it is read from the process environment. If the app instead pauses at startup logging “Database not ready (attempt N)”, that is the bounded retry window — it buys time for a slow database, not for a wrong one.

“database files are incompatible with server” on docker compose up

FATAL:  database files are incompatible with server
DETAIL: The data directory was initialized by PostgreSQL version 16,
        which is not compatible with this version 15.x

Cause: the Docker volume keeps the database files between runs, stamped with the PostgreSQL major version that created them. If the image: tag points at an older major version than the volume's PG_VERSION, PostgreSQL refuses to start.

Fix (non-destructive, preferred): set the image to the major version matching the data — currently postgis/postgis:16-3.4 — and docker compose up -d again. Check what the volume holds with:

docker run --rm -v feedbackapp_postgres_data:/data alpine cat /data/PG_VERSION

Fix (destructive): if the data is disposable, docker compose down -v and let the pinned image re-initialize — this erases both the database and pgAdmin volumes.

Sync fails with HTTP 400 “database has not been seeded with targets yet”

POST /api/sync returns this when the commit fails — most commonly because feedback references anomalies that do not exist in the current database (it was wiped, re-ingested, or you are on the SQLite fallback). Load targets first, then sync again; queued items are preserved in the browser until a sync succeeds. Check the server log for Skipping sync of feedback log … lines, which name the orphaned records.

Map shows no points after login

Usual causes, in order: the backend is not running; the database is empty (seed or ingest); or active filters exclude everything — reset them to “All”.

Offline mode is not working

Open DevTools → Application → Service Workers; confirm the worker is activated and look for Precache skipped: warnings in the console. Remember that renaming CACHE_NAME is what evicts a bad cache (§12.3), and that map tiles are never precached. A hard reload with “Update on reload” checked is the fastest way to get a clean worker.

Mobile layout looks like the desktop one

Check that the cssTarget pin in vite.config.ts is still there (§11.4).

Taking a backup

The database holds the users table, so dumps are sensitive; .gitignore excludes backup-*.sql for that reason, so keep that naming. Take one before anything destructive:

docker exec feedback_postgres_db pg_dump -U postgres nolte_geoservices > backup-nolte_geoservices-<timestamp>.sql

17.2 Still live — worth fixing

  • POST /api/seed wipes the database on one call. It is admin-gated now, but that is the only thing between a careless click or a borrowed admin session and every excavation record in the system. It deserves a confirmation token, or simply not being reachable in a production build.
  • Open CORS. allow_origins=["*"] with allow_credentials=True — convenient in development, wrong anywhere else. Any page on any origin can call this API; the only thing standing in the way is possession of a bearer token.
  • N+1 query pattern. GET /api/points runs one feedback query per anomaly — fine for hundreds of targets, slow for the full ~2,400-target magnetic dataset. Worse than it first looks, because /api/stats and /api/sync both call it internally, so every sync round-trip pays the cost. A join or eager-load would fix it.
  • Photos as base64 in the database will bloat rows quickly; object storage with references and thumbnails would scale better. They also travel inside the sync payload, which is the slowest part of a field upload.
  • Keyword-based UXO detection. Searching notes for “mine”, “bomb”, … is fragile — a note reading “nothing resembling a mine” classifies as UXO. An explicit status chosen by the investigator would be more reliable, and this is the one classification where a false negative is a safety matter.
  • Single hard-coded project. 11-24-2736 is baked into the import and seed paths and into ingest_anomalies.py. Multi-project support is scaffolded (the projects table, the dropdown, the SQL migrations for 11-26-5151) but not finished.
  • Duplicated conversion math in Python, TypeScript (twice) and SQL — four implementations to keep consistent. The Python/TS versions also ignore the small geoid differences a library like pyproj/proj4js would handle.
  • No automated tests and no CI. Only ad-hoc UTM conversion scripts exist (test_utm.py, scratch/). doctor.py is CI-ready and would be a reasonable first gate.
  • PostGIS extension errors are only logged. The enable step in init_db() catches and logs on failure, so a failed PostGIS setup continues silently into a broken trigger installation.
  • Deployment. Everything runs locally — uvicorn plus Docker, no HTTPS, no process supervision, and no backup or retention policy for the Postgres volume.

17.3 Setup gotchas — the things that actually cost time

  • Three unrelated passwords (§15.1). POSTGRES_PASSWORD is inert on an existing volume; the password inside DATABASE_URL is the one that connects; pgAdmin's is a third thing entirely.
  • ALLOW_SQLITE_FALLBACK is read from the process environment, not .env (§15.1). Putting it in .env does nothing at all.
  • The sample CSVs must stay at the repository root (§10). ingest_anomalies.py resolves them — and .env — as bare relative paths against the working directory.
  • pandas is not in requirements.txt although ingest_anomalies.py imports it. Install it separately, or the ingestion fails at import. Known gap; to be pinned.
  • install_node.py hardcodes its target directory as c:\Apps\feedbackapp\node. On any other machine, edit TARGET_DIR or install Node yourself. Known gap; to be made relative to the script.
  • static/ is committed build output. Frontend changes are only live after npm run build, and that rebuild belongs in its own commit.
  • SEED_PASSWORD only applies to an empty users table. After that it is ignored, which reads as “it did nothing”.
