Standard Operating Procedure & Engineering Manual

ETL Pipeline: Architecture & Operations Guide

Complete handbook for running, updating, and extending project ingestion without AI assistance

1. ETL Directory Structure & File Map

The ETL pipeline lives completely in the root etl/ directory. Everything project-specific is configuration-driven; code and business logic are decoupled.

File / Directory Role & Responsibility
config/projects.yml The single source of configuration. Defines project schemas, source tables, column mappings, SRID coordinates, and target ID formatting.
dbt/models/ SQL transformation models that standardize raw schema data into clean anomaly candidates (stg_candidates.sql, int_candidates.sql).
dbt/macros/etl_columns.sql Jinja SQL macros converting coordinate roundings, category regex fallback, and target ID generation.
dbt/tests/ Automated data contracts ensuring zero orphaned feedback, UUID5 consistency, and spatial index existence.
runner/run.py Python orchestrator handling database connections, advisory locks, UUID generation, sequential VM numbers, and atomic transactional merges.
Dockerfile Lightweight Python container with dbt-postgres and psycopg.
docker-compose.yml Defines the etl runner and etl-approve CLI containers under the --profile etl flag.

2. How the Pipeline Works (Architectural Flow)

The pipeline synchronizes raw geophysical inspection tables (e.g. Köln picks, Wilhelmshaven Magnetic & Georadar) into public.anomalies and per-project <schema>.anomalie_1.

┌─────────────────────────────────┐
│ Project Schemas (e.g. Postgres) │  (Defined in etl/config/projects.yml)
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│ dbt: stg_candidates (View)      │  Extracts coords, reprojects to EPSG:4326, cleans categories
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│ Runner: register_ids (Python)   │  Computes deterministic uuid5(NAMESPACE_DNS, target_id)
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│ dbt: int_candidates (Table)     │  Deduplicates coordinates, applies approved alias mappings
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│ Runner: merge (Single Tx)       │  1. Inserts new targets (status='pending', sequential VM nr)
│                                 │  2. Stages attribute changes into etl.change_log
│                                 │  3. Stages coordinate shifts into etl.correction_candidates
│                                 │  4. Runs safety verification gates (abort on rollback)
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│ public.anomalies & anomalie_1   │  Application database updated safely
└─────────────────────────────────┘

Core Principles & Protection Mechanisms

  • Least Privilege & Immutability: The etl_pipeline database user has NO DELETE, TRUNCATE, or direct UPDATE rights on public.anomalies. Data can never be deleted accidentally.
  • Human-in-the-Loop Decisions: If a source row changes (category, depth, layer, or position), it is staged in etl.change_log. An approver must explicitly approve it before the change writes to production.
  • Sequential VM Numbers: Existing targets keep their VM numbers. New targets receive the next unused sequence number per project from etl.vm_registry.
  • Safety Gates: Before committing the database transaction, the runner verifies that zero feedback rows were disconnected, no VM numbers collided, and no IDs drifted. If any gate fails, the transaction rolls back cleanly.

3. Command Reference & Daily Operations

All commands run from the repository root via Docker Compose.

Triggering Ingestion Runs

# 1. Standard run (checks fingerprint; skips if no data or config changed)
docker compose --profile etl run --rm etl run

# 2. Forced run (forces execution regardless of change detection)
docker compose --profile etl run --rm etl run --force

# 3. Scheduled continuous loop (runs every N seconds configured in .env)
docker compose --profile etl up -d etl

Reviewing and Approving Staged Changes

# Check current pipeline status, unconfigured tables, and pending changes
docker compose --profile etl run --rm etl-approve

# Approve specific attribute changes (e.g. Category or Depth update)
docker compose --profile etl run --rm etl-approve approve-change 12 13

# Reject specific attribute changes
docker compose --profile etl run --rm etl-approve reject-change 12

# Approve a coordinate correction pair (keeps existing target ID & feedback, updates coords)
docker compose --profile etl run --rm etl-approve approve-correction 5

# Reject a coordinate correction (treats the point as a brand-new anomaly instead)
docker compose --profile etl run --rm etl-approve reject-correction 5
Applying Approved Decisions
When you approve changes using etl-approve, they are recorded as approved in the approval ledger. To actually execute and merge them into public.anomalies, simply run docker compose --profile etl run --rm etl run.

4. How to Update & Add New Projects or Tables

Because the pipeline is completely configuration-driven, you do not write Python code to add data. Follow these 4 standard steps:

Step 1: Edit etl/config/projects.yml

Open etl/config/projects.yml and add your project configuration under projects:

  - project_id: "11-25-3333"              # Unique project code
    project_name: "Duesseldorf Hafen"     # Human-readable title
    schema: p_11_25_3333_duesseldorf     # Postgres schema name
    srid: 25832                          # Spatial Reference System Identifier (e.g. UTM 32N)
    vm_prefix: "3333"                    # Prefix for sequential VM numbers (e.g. 3333-1)
    sources:
      - table: anomalies_raw             # Source table inside the schema
        instrument: georadar             # "georadar" or "magnetic"
        key: id                          # (Optional) Primary key column in source table
        id_decimals: 3                   # Precision for target_id string
        columns:
          easting: x_coord               # Column name for Easting / X
          northing: y_coord              # Column name for Northing / Y
          depth: { column: depth_m, round: 2 } # Depth column (or null)
          category: { column: category } # Category column (e.g. Kat-1)
          layer: layer                   # Layer column (or null)

Step 2: Grant Permissions to etl_pipeline

The pipeline role needs PostgreSQL read access to the new schema. Run:

# Generate grants based on the updated projects.yml
docker compose --profile etl run --rm --no-deps etl setup-sql > setup.sql

# Execute grants against PostgreSQL as superuser
docker exec -i feedback_postgres_db psql -U postgres -d nolte_geoservices -v ON_ERROR_STOP=1 < setup.sql

Step 3: Test and Verify the Ingestion

# Run forced ingestion
docker compose --profile etl run --rm etl run --force

# Inspect status summary
docker compose --profile etl run --rm etl-approve
Important: Adding New Instruments
If your new table introduces an instrument other than georadar or magnetic (e.g., tdem), add that value to the accepted list in etl/dbt/models/schema.yml under stg_candidates -> instrument -> accepted_values so that dbt tests will pass.
